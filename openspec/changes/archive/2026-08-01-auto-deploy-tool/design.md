## Context

本项目从零构建一个自动部署工具，面向隔离互联网的服务器环境。技术栈已确定：Spring Boot 2.7 + MyBatis-Plus + Thymeleaf（前后端不分离），Apache Shiro（认证授权），MySQL 作为数据库，存储项目配置和构建历史。核心约束：部署服务器无互联网访问，构建可在本机或可联网的构建服务器上进行。

## Goals / Non-Goals

**Goals:**
- 设计清晰的分层架构，支持构建、部署、配置管理三大核心流程
- 实现配置热加载机制，确保配置变更不影响正在进行的构建
- 设计线程池并发模型，支持可配置的并发构建
- 设计 SSE 日志推送机制，实现构建过程实时可观测
- 设计安全凭证管理方案，所有敏感信息通过环境变量读取
- 设计多语言版本隔离方案，基于语言原生多版本管理工具

**Non-Goals:**
- 不实现分布式构建（单节点部署）
- 不实现容器化部署（直接 SSH+SCP 部署）
- 不实现 RBAC 细粒度权限管理（仅支持注册登录）
- 不实现邮件/消息通知系统

## Decisions

### 1. 架构分层：Spring Boot MVC 三层架构

**决策**：采用 Controller → Service → Repository(Mapper) 三层架构，基于 Spring Boot 自动配置。

**理由**：Spring Boot 自动配置简化了 XML 配置，MyBatis-Plus 的 BaseMapper 提供 CRUD 开箱即用。Thymeleaf 前后端不分离场景下 Controller 直接返回视图。项目规模适中，三层架构足够清晰。

**备选**：六边形架构 — 过度设计，不适用于此规模。

### 2. 配置即时生效：MySQL 数据库 + 构建快照

**决策**：项目配置存储在 MySQL 数据库中，通过 Web 页面或 HTTP 接口修改后立即提交到数据库，新配置即时生效。构建任务启动时从数据库读取当前配置并创建快照对象，后续不受配置变更影响。

**理由**：MySQL 事务保证数据一致性，配置修改即时生效无需文件监听。构建任务持有配置快照对象，实现"不影响正在进行的构建"。

**备选**：WatchService 监听 JSON 文件 — 需要 JDK WatchService 且跨平台兼容性差。Spring `@RefreshScope` — 需要 Spring Cloud 依赖，过重。

### 3. 并发构建：线程池 + 任务队列

**决策**：使用 `ThreadPoolExecutor`，核心线程数和最大线程数均设为配置的并发数（默认 20），无界 `LinkedBlockingQueue` 作为等待队列。每个构建任务作为 `Runnable` 提交到线程池。

**理由**：ThreadPoolExecutor 提供成熟的线程管理和队列机制。无界队列确保超出的任务排队等待而非拒绝。并发数可动态配置，通过重建线程池实现。

**备选**：`ForkJoinPool` — 适合分治任务，不适合独立的构建任务。

### 4. SSE 日志推送：SseEmitter + 进程输出流转发

**决策**：构建任务通过 `ProcessBuilder` 启动子进程，读取子进程的 stdout/stderr 流，通过 `SseEmitter` 推送到前端。同时写入日志文件。使用阻塞队列在进程读取线程和 SSE 推送线程间缓冲。

**理由**：SseEmitter 是 Spring MVC 原生 SSE 支持。ProcessBuilder 提供进程管理和工作目录设置能力。阻塞队列解耦日志生产和消费。

**备选**：WebSocket — 双向通信不是需求，SSE 更简单。轮询 — 实时性差，浪费带宽。

### 5. 数据存储：MySQL + MyBatis-Plus + 文件系统

**决策**：项目配置和构建历史使用 MySQL 数据库（通过 MyBatis-Plus + HikariCP 连接池），构建日志使用文件系统存储。

**理由**：MyBatis-Plus 提供 BaseMapper CRUD、条件构造器、分页插件等开箱即用功能，减少样板代码。MySQL 支持事务和并发访问。构建日志为顺序写入的大文本，适合文件系统存储，便于按保留天数清理。

**备选**：SQLite — 零配置但并发写入受限。H2 数据库 — 内嵌但通用性不如 MySQL。

### 6. 敏感信息管理：环境变量引用

**决策**：数据库配置中仅存储环境变量名（如 `GIT_TOKEN_ENV`），系统运行时通过 `System.getenv()` 读取实际值。系统设置页面提供环境变量名管理，不展示实际值。

**理由**：环境变量是操作系统级的安全实践，不将敏感信息写入文件。用户可灵活配置不同的环境变量。

**备选**：加密存储 — 需要管理密钥，增加复杂度。Java KeyStore — 过重。

### 7. 多语言版本隔离：语言原生版本管理工具

**决策**：
- Node：使用 nvm，构建前通过 `nvm use <version>` 切换版本
- Python：使用 uv，构建前通过 `uv venv` 创建虚拟环境
- Java：使用 SDKMAN，构建前通过 `sdk use java <version>` 切换
- Go：使用 gvm，构建前通过 `gvm use <version>` 切换

构建指令执行前，系统自动在构建脚本前添加版本切换命令。

**理由**：使用语言社区主流的多版本管理工具，避免重新造轮子。每个构建任务独立切换版本，互不影响。

**备选**：Docker 容器隔离 — 部署服务器无互联网，不适合。

### 8. SSH 操作：Apache MINA SSHD

**决策**：使用 Apache MINA SSHD 进行 SSH 连接、远程命令执行和 SCP/SFTP 文件传输。远程构建产物由后端通过 SCP 从构建服务器下载到本地，再通过 SCP 上传到部署服务器。

**理由**：纯 Java 实现，功能全面（SSH + SCP + SFTP），活跃维护。JSch 已停止维护。后端直接 SCP 传输避免浏览器 HTTP 传输大文件的限制。

**备选**：JSch — 已停止维护。sshj — 社区较小。

### 9. Git 操作：JGit

**决策**：使用 JGit 进行 Git 仓库克隆和拉取操作。

**理由**：纯 Java 实现，无需系统安装 Git 命令行工具。支持认证（用户名密码、Token、SSH Key）。

**备选**：调用 Git 命令行 — 依赖系统安装 Git，且解析输出不便。

### 10. 用户认证：Apache Shiro + 不可逆哈希加盐

**决策**：使用 Apache Shiro 进行认证授权、会话管理和访问控制。密码加密采用不可逆哈希算法加盐方案，由 Shiro 的 `HashedCredentialsMatcher` 负责哈希计算和盐管理。前端将密码不可逆哈希后以密文形式传输，后端通过 Shiro 生成随机盐并存储哈希值+盐。

**理由**：Apache Shiro 提供认证、授权、会话管理、加密等完整功能，配置简洁，集成 Spring MVC 方便。Shiro 的 `HashedCredentialsMatcher` 内置盐管理和哈希迭代支持，安全性优于手动实现。前端哈希避免明文传输，后端加盐防止彩虹表攻击。Shiro 过滤器链替代手动拦截器，访问控制更规范。

**备选**：Spring Security — 功能强大但配置复杂，对简单注册登录场景过重。手动 HttpSession+拦截器 — 需自行实现会话管理和访问控制逻辑。JWT — 前后端不分离架构下无优势。

## Risks / Trade-offs

- **[MySQL 连接池管理]** → 高并发构建时数据库连接可能成为瓶颈。使用 HikariCP 连接池，合理配置连接数，构建记录写入使用异步队列缓冲
- **[SSE 连接管理]** → 长时间构建可能导致 SSE 连接超时。设置合理的超时时间，前端实现自动重连
- **[子进程日志编码]** → Windows 上子进程输出可能使用 GBK 编码，需根据操作系统设置正确的字符集读取
- **[构建服务器单点]** → 仅支持配置一台构建服务器，若构建服务器不可用则只能使用本机构建。未来可扩展多构建服务器
- **[环境变量可见性]** → 环境变量需在系统启动前设置好，运行时修改环境变量需要重启系统。通过系统设置页面管理变量名映射，实际值由运维配置
- **[构建服务器与部署服务器网络可达性]** → 后端 SCP 传输要求本机可同时访问构建服务器和部署服务器。若网络不通则无法完成远程构建部署，需确保网络可达性
